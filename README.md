# Рюкзак: bitset, SIMD и многопоточность — с замерами и профилированием

Четыре реализации 0/1-рюкзака (достижимость сумм), измеренные через **Google Benchmark**,
плюс инструкция, как посмотреть на всё это в **flame graph** и счётчиках `perf`.

Проект отвечает на вопрос из разговора: *«bitset + SIMD + потоки = колоссальное ускорение?»* —
и честно показывает, где интуиция верна, а где реальность вносит поправки.

## Быстрый старт

```bash
sudo apt install g++ libbenchmark-dev      # зависимости
make verify     # проверить, что ручная пословная версия == std::bitset
make bench      # главный бенчмарк (4 версии)
make why        # почему naive НЕ в 64 раза медленнее (скаляр vs AVX vs bitset)
make asm        # увидеть SIMD-инструкции (ymm/zmm) в дизассемблере
```

Число потоков для многопоточной версии: `OMP_NUM_THREADS=8 ./bench_knapsack`.

## Четыре версии (файл `bench_knapsack.cpp`)

1. **naive_vector** — `vector<uint8_t>`, внутренний цикл `dp[j] |= dp[j-x]`.
2. **bitset** — `dp |= dp << x` (in-place, работа 64-битными словами).
3. **twolayer_serial** — два слоя (`old`→`new`), один поток. Убирает in-place-зависимость.
4. **twolayer_omp** — тот же двухслойный, но новый слой разрезан по ядрам через OpenMP.

Ключ к версиям 3–4: чтобы **распараллелить**, пришлось уйти от удобного `std::bitset`
к ручному массиву `uint64_t[]` — потому что `bitset` не даёт разрезать себя по словам
между потоками. Контроль над раскладкой в памяти — цена за параллелизм.

## Результаты на одном ядре (песочница, AVX-512, 1 CPU)

```
naive_vector      3.36 ms
bitset            1.49 ms   (×2.3 над naive)
twolayer_serial   1.33 ms   (×2.5)  — чуть быстрее bitset: меньше проходов по памяти
twolayer_omp      1.30 ms   (×2.6)  — на 1 ядре потоки не дают ничего (ожидаемо)
```

### Куда делся обещанный «×64»?

Теория говорила: bitset обрабатывает 64 бита за слово → ×64 над «один-бит-за-раз».
Но замер (`make why`) показывает правду:

```
naive СКАЛЯРНО (AVX запрещён):  45.15 ms   ← вот это настоящий «один-бит-за-раз»
naive ВЕКТОРИЗОВАНО (AVX сам):   2.82 ms   ← компилятор САМ применил SIMD к БАЙТАМ, ×16!
bitset:                          1.18 ms   ← ×38 над скалярным, но ×2.4 над векторным
```

Три вывода:

- **Над честно-скалярным наивом bitset и правда даёт ×38** — близко к теоретическому ×64,
  срезано упором в память.
- **Но такого наива в реальности нет:** компилятор на `-O3 -march=native`
  **сам векторизует даже байтовый цикл** (`vpor ymm` — ИЛИ 32 байта за инструкцию),
  давая ×16 бесплатно. `make asm` показывает эти инструкции.
- **Реальный выигрыш bitset над тем, что компилятор строит фактически, — ~×2.4**,
  и идёт он от 8-кратной плотности (бит вместо байта → в 8 раз меньше памяти гонять).

Это и есть ценность замера: теоретический множитель сравнивал с несуществующим
скалярным кодом. Померили — увидели настоящую картину.

## Что будет на нескольких ядрах (запусти у себя!)

На 1-ядерной песочнице `twolayer_omp` не ускоряется. У тебя на 4–8 ядрах — ускорится,
**но не линейно**, и вот почему это главный урок:

Операции над bitset — **memory-bound** (упираются в пропускную способность памяти,
а не в скорость вычислений: на байт данных приходится всего одно ИЛИ). А пропускная
способность RAM — **общий ресурс на все ядра**. Поэтому:

- 2–4 потока насыщают шину памяти и дают ускорение ~×2–3;
- дальнейшие ядра почти ничего не добавляют — они просто ждут память.

Проверь это напрямую:

```bash
for t in 1 2 4 8; do
  echo "=== $t поток(ов) ==="
  OMP_NUM_THREADS=$t ./bench_knapsack --benchmark_filter=BM_4 --benchmark_min_time=1s
done
```

Увидишь, как ускорение выходит на плато раньше числа ядер — вживую упрёшься
в memory bandwidth. (Спор из разговора: двухслойная схема параллелится **корректно**,
но масштабируется плохо именно из-за memory-bound природы, а не из-за зависимостей.)

## Профилирование: flame graph и perf

`perf` требует доступа к ядру и в контейнерах/песочницах не работает — запускай на своей
машине (или на своей ВМ; в Hyper-V может понадобиться донастройка).

### Flame graph — где программа проводит время

Flame graph отвечает на вопрос «на что уходят такты внутри ОДНОЙ программы»:
ось X — доля времени (шире = дольше), ось Y — глубина стека вызовов.

```bash
# один раз: взять скрипты
git clone https://github.com/brendangregg/FlameGraph

# записать профиль и построить SVG (цель есть в Makefile)
make flamegraph          # внутри: perf record + stackcollapse + flamegraph.pl
# открыть flame.svg в браузере — кликабельно, с поиском
```

Вручную то же самое:
```bash
perf record -F 999 -g --call-graph dwarf -- ./bench_knapsack --benchmark_filter=BM_1
perf script | ./FlameGraph/stackcollapse-perf.pl | ./FlameGraph/flamegraph.pl > flame.svg
```

Для рюкзака flame graph менее интересен (горячая точка одна — цикл обновления), поэтому
для *сравнения версий* точнее Google Benchmark, а не пламя. Flame graph раскрывается,
когда программа большая и неясно, что тормозит.

### perf stat — подтвердить, что упор в память

Вот это для нашей задачи показательнее пламени — прямые счётчики железа:

```bash
make perfstat
# или вручную:
perf stat -e cycles,instructions,cache-references,cache-misses,LLC-load-misses \
    ./bench_knapsack --benchmark_filter=BM_4
```

Смотри на **LLC-load-misses** (промахи последнего уровня кэша → поход в RAM) и на
**instructions per cycle (IPC)**. Низкий IPC при высоких промахах кэша = процессор
простаивает в ожидании памяти — вот числовое доказательство memory-bound. Именно поэтому
лишние ядра не помогают.

### Другие инструменты, которые стоит знать

- **`perf top`** — живой профиль системы, как `htop` для функций.
- **Valgrind Callgrind + KCachegrind** — точный (инструментальный, медленный) профиль
  с графом вызовов и аннотацией исходника: `valgrind --tool=callgrind ./prog`, потом
  `kcachegrind callgrind.out.*`.
- **`perf annotate`** — показать, на каких *инструкциях* ассемблера горит время
  (связка с ликбезом: увидишь, какая машинная строка дорогая).

## Итоговая картина ускорения (честная)

| Уровень | Множитель | Откуда |
|---|---|---|
| bitset над **скалярным** наивом | ~×38 | 64 бита за слово |
| ...но компилятор сам векторизует байты | ×16 «съедается» | автовекторизация (SIMD) на `-O3` |
| bitset над **реальным** (векторным) наивом | ~×2.4 | 8× плотность (бит vs байт), memory-bound |
| SIMD над bitset (AVX-512 vs 64-бит) | ×2–4 | шире слово, минус сдвиг через границы |
| потоки (двухслойно) | ×2–3, плато | memory bandwidth — общий ресурс |

Реальное ускорение bitset-рюкзака над «наивным как в учебнике» — **десятки раз** (ты был прав
в ощущении), но собрано оно из плотности + SIMD в одном потоке, а многоядерность упирается
в память быстрее, чем в число ядер.
